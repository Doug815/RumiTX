DMR007 Binary Protocol (DOOGEE S80)
====================================
Discovered from HcTTalkie.vdex decompilation, 2026-10-11.

MODULE IDENTIFICATION:
- ro.hct_talkie_support_type = "digital" → DMR007 = true
- ATCommond.DMR007 boolean flag controls protocol selection

FRAME FORMAT (all frames):
- Start: 0x68
- End: 0x10
- Checksum: Internet checksum (one's complement) as 2-byte hex

SERIAL PORT (corrected 2026-10-11 run 8/16):
- /dev/ttyMT1, **57600 8N1** raw. The stock app passes 57600 to
  openSerialPort (const v0, #+57600 at both the Application and
  SerialPortService call sites, oatdump-HcTTalkie.txt lines 52129/69480).
- The rumitx-ptt helper's "serial" command configures **9600** 8N1 --
  WRONG baud (a stale guess). All early "no reply" mysteries (run 3/16)
  were this baud mismatch; everything works at 57600. The RumiTX app
  configures the port itself via `su -c "stty -F /dev/ttyMT1 57600 raw
  -echo"` (the deployed helper binary is not touched).

PHYSICAL PTT BUTTON (decoded 2026-10-11 run 8/16, no phone needed):
- Fragment_speak.onKeyDown/onKeyUp handle a 3-key sparse-switch:
  keys {24, 25, ?} where 24/25 = KEYCODE_VOLUME_UP/DOWN (confirmed by
  the setVolume(+1/-1) calls in the onKeyUp case bodies).
- The third key's case logs "onKeyDown KEYCODE_F9 FLAG_LONG_PRESS" /
  "onKeyUp KEYCODE_F9" and fires the PTT down/up callback (vtable@125).
  -> the side PTT button reports as **KEYCODE_F9 = 139**.
- Behavior (mirrored in RumiTX MainActivity): onKeyDown keys PTT only
  when KeyEvent.getFlags() has FLAG_LONG_PRESS (0x80) set; plain
  key-down is consumed without keying. onKeyUp always releases.
  (The third switch key's raw value was display-truncated in the oatdump;
  139 is inferred from the app's own "KEYCODE_F9" log label. Android
  KEYCODE_F9 = 139.)

CHECKSUM (checkSpaceSum):
1. Split hex string by spaces
2. Pair bytes into 16-bit big-endian words
3. Sum with carry folding
4. XOR with 0xFFFF (one's complement)
5. Format as 4-digit hex, split as "XX XX"

SEND START/STOP FRAME (PTT):
Format: 68 06 01 <send> <cksum> 00 04 <calltype> <callnumber:3 bytes> 10
- send: "01" = start TX, "FF" = stop TX
- calltype: hex string (typically "00")
- callnumber: 3-byte hex string (typically "00 00 00")
- Example start: 68 06 01 01 86 F4 00 04 00 00 00 00 10
- Example stop:  68 06 01 FF 85 F6 00 04 00 00 00 00 10

TX SEQUENCE:
1. Send "send start" frame over serial (/dev/ttyMT1)
2. Wait for "sendstart" reply from module
3. Fire ppt_down ioctl (0x40046903) on /dev/hctintercom_node
4. On release: send "send stop" frame, then ppt_up ioctl (0x40046904)

CHANNEL PROGRAMMING FRAMES (fully decoded 2026-10-11 from ATCommond.getATSetGroup):
Source: /tmp/oatdump.txt, ATCommond.getATSetGroup(HashMap) @ file line 50690.
DMR007=true + talkie=="1" (digital) -> 68 36 frame.
DMR007=true + talkie!="1" (analog)  -> 68 35 frame.
DMR007=false -> text "AT+DMOSETGROUP=<gwb>,<tfv>,<rfv>,<cxcss>,<sq>,<cxcss>,<flag>".
Caller builds the HashMap from a Channel bean with keys: gwb, tfv, rfv, cxcss,
sq, flag, txtype, rxtype, colorcode, phoneid, calltype, callnumber, encry,
secretkey, recgroup, talkie, txcxcss, rxcxcss.

68 36 DIGITAL CHANNEL FRAME:
Layout: 68 36 01 01 <CS:2B> 00 <LEN:1B> <payload> 10
- CS = checkSpaceSum("68 36 01 01 00 00 " + "00 <LEN>" + " " + payload + " 10"),
  formatted with decimalToHex(sum, true, false) -> "XX XX" big-endian.
- LEN = payload byte count (space-separated tokens). Standard digital
  channel = 156 bytes -> "00 9C".
- payload, in order (all via StringUtils, see below):
  [0]     flag            1B  stringToHex(flag,1,0) = Channel.getFlag();
                                                 semantics not fully determined
                                                 (DB-driven; editor not in this
                                                 vdex) -- "1" live-verified,
                                                 factory stock channel used 0x01
  [1-4]   TX frequency    4B  rfv in Hz, LITTLE-ENDIAN u32
                                                 (stringToHexWidthByte(hz,1,1,4);
                                                 the ONLY LE field in the frame)
  [5-8]   RX frequency    4B  same encoding (simplex: same value)
  [9-12]  phoneid         4B  radio's own DMR ID: BIG-ENDIAN digits,
                                                 LEFT-padded with "00" to 4 B
                                                 (stringToHexWidthByte(id,1,0,4):
                                                 "1" -> "00 00 00 01",
                                                 "12345" -> "00 00 30 39").
                                                 CORRECTED 2026-10-11 run 13/16:
                                                 runs 6-12 misread this as LE
                                                 ("00 00 39 30") from the
                                                 module echo, which only
                                                 reflected our own frame.
                                                 The dex passes reverse=false
                                                 for every ID field; the
                                                 module expects BE (it feeds
                                                 bytes [1:4] to the 24-bit
                                                 DMR destination ID).
  [13]    colorcode       1B  DMR color code 0-15 (stringToHex(cc,1,0))
  [14]    calltype        1B  TX call type (0 = group call, 4 = private call)
                                                 (stringToHex(ct,1,0))
  [15-18] callnumber      4B  TX talkgroup / ID, same BE ID encoding.
                 Stock "unset" = "16777215" -> "00 FF FF FF"
                 (= DMR "invalid" ID; ambiguous BE/LE, dex says BE)
  [19]    encry flag      1B  "01" if encry=="0", else "FF" (dex-verified:
                 if-eqz on encry.equals("0") -> "01" path, else v9="FF")
  [20-27] secretkey       8B  encryption key, BE, left-padded to 8 B
                 (stringToHexWidthByte(key,1,0,8)); zeros when encry=="0"
  [28-155] recgroup       128B  32 slots x 4B BE, same ID encoding;
                 slot = stringToHexWidthByte(group,1,0,4), empty -> "00 00 00 00".
                 QUIRK: single-char entries are SKIPPED (len==1 -> zeros),
                 so pad one-digit groups: "1" -> "01".
- Frequency encoding: rfv "446.5555" -> split on "." -> "446"+"5555" -> +"00"
  -> "446555500" = Hz as decimal string -> int -> LE hex bytes.
  (App always uses 4 decimals, e.g. checkFrequencyRang "400.0000"-"470.0000";
  module UHF range is 400-470 MHz. Fewer decimals give wrong Hz.)
  446.5555 MHz -> 0x1A9DE56C -> wire bytes "6C E5 9D 1A".

TONE ENCODING (68 35 analog frame) -- DECODED 2026-10-11 run 15/16
Source: stock-talkie.apk resources (array/csstype, string/ctcss, string/cdcss)
+ Fragment_Analog dex (oatdump-HcTTalkie.txt lines 77449-78445).
- csstype (Channel field; feeds BOTH txtype and rxtype map keys): index
  into array/csstype = ["Carrier", "CTCSS", "CDCSS", "Reverse CDCSS"],
  i.e. "0" = carrier squelch (no tone), "1" = CTCSS, "2" = CDCSS (DCS
  normal), "3" = Reverse CDCSS (DCS inverted). Factory default "2".
  (Note: the stock picker's initial-highlight passes parseInt-1, a
  harmless off-by-one in the stock UI; stored values are 0-based.)
- txcxcss/rxcxcss: tone CODE INDEX as decimal string -> 1 byte each.
  The stock tone picker (title "CTCSS/CDCSS") offers:
    csstype == "3" -> 51 options, indices 0-50 (built from the
                     "CTCSS %d" label array)
    otherwise      -> 83 options, indices 0-82 (built from the
                     "CDCSS %d" label array)
  The user picks a bare index number; the module resolves the index
  through its own internal tone tables. Factory default "1".
  OPEN: physical tone (Hz / DCS code) per index -- needs live module
  programming + readback; the app never stores physical tone values.
- Factory default analog channels (res/xml/default_talkie_channel.xml):
  20 channels, 409.7500 MHz + 12.5 kHz steps (409.7500-409.9875),
  narrow, squelch "2", flag "1", csstype "2" (CDCSS), tone code "1",
  phoneid = channel number (1-20), msgtype "2", encry "1",
  secretkey "12345678".

CHECKSUM SUB-0x100 QUIRK (found + fixed 2026-10-11 run 11/16):
- Stock StringUtils.decimalToHex(v, space=true, reverse=false) only
  pair-spaces when the hex digit count is > 2 (dex-verified at
  oatdump-HcTTalkie.txt line 61373: `if-le length, 2` skips spacing).
  For checksum values < 0x100 the result is a SINGLE token: 0x00AA ->
  "AA", not "00 AA".
- Consequence: any frame whose Internet checksum is < 0x100 goes out
  1 byte short. Observed live: our 68 35 analog frame (checksum 0x00AA)
  was sent as 23 bytes "68 35 01 01 AA 00 0F ..." -> module replied
  "68 35 00 01 87 C9 00 00 10" (sr=0x01, NOT sr=0x09 cksum -- the module
  does not flag it as a checksum error) and did NOT program the channel
  (CHECK-AC stayed zeros). The stock app has the same latent bug.
- FIX (RumiTX only): dmr007_frame.checksum_hex() (Python) and
  Dmr007Frame.checksumHex() (Java) always emit 2 bytes big-endian.
  All frame builders (68 06, 68 07, 68 35, 68 36, 68 02, queries) now
  use it; decimalToHex keeps its faithful stock behavior for other
  fields (none of which need 2-byte output). Verified: all previously
  live-verified vectors byte-identical (checksums were all >= 0x100);
  corrected 68 35 -> module SUCCESS + readback match (see above).
  APK rebuilt 2026-10-11 ~07:47 CDT with the fix (RumiTX-debug.apk).

STRINGUTILS ENCODING (exact):
- decimalToHex(int v, bool space, bool reverse): hex digits big-endian;
  odd digit count -> leading "0"; v==0 -> "00". If space && digits>2: split
  into byte pairs, REVERSE pair order if reverse, join with " ".
  So (x,true,true) = little-endian byte string; (x,true,false) = big-endian.
- stringToHex(str, b, b) = decimalToHex(int(str), b, b).
- stringToHexWidthByte(str, b, b, width): as above, then LEFT-pad with "00"
  tokens to `width` bytes (only the space=true path is used by these frames).
  With reverse=true the digit pairs are LE-ordered but the padding stays
  left: "12345" -> "39 30" -> "00 00 39 30". With reverse=false the digits
  stay big-endian: "12345" -> "30 39" -> "00 00 30 39".
  DEX AUDIT (run 13/16): frequencies use (1,1) = LE; EVERY ID field
  (phoneid, callnumber, recgroup slots, secretkey, 68 06 + 68 07
  destinations) uses (1,0) = BE. Runs 6-12 wrongly claimed LE for IDs.
- string2Unicode(str, spaceFirst): per char, Integer.toHexString(c),
  left-padded to 4 hex digits ("41"->"0041"); if spaceFirst, byte-pairs are
  space-separated ("00 41") and each char is followed by a space, so the
  result ends with a trailing space: "hi" -> "00 48 00 69 ".
- checkSpaceSum(str): split on " ", sum 16-bit big-endian words
  ((b0<<8)|b1); odd trailing byte counts as (b<<8); fold carries
  (sum = (sum&0xFFFF)+(sum>>16) until no carry); return sum ^ 0xFFFF.
  Verified: "68 06 01 01 86 F4 00 04 00 00 00 00 10" checksums over the
  "00 00"-placeholder form to 0x86F4.

MODULE REPLY PROTOCOL (from ReceiveDataPort.onReceive, oatdump-HcTTalkie.txt):
- The serial RX thread converts bytes to a SPACELESS UPPERCASE hex string
  (StringUtils.bytesToHexString: 2 hex chars per byte, no separators).
- The DMR007 binary path SKIPS the checksum verification entirely
  (checkSum is only called on the non-DMR007 text path). It parses:
  cmd = hex.substring(2,4)   (byte[1])
  sr  = hex.substring(6,8)   (byte[3])
  and classifies by EXACT 2-char equality (CORRECTION to the earlier
  "substring contains" note: for 2-char operands contains() == equals(),
  and the operands here are the extracted 2-char fields, not the whole
  hex string -- so the semantics are exact field equality):
  "00".equals(sr)            -> SUCCESS
  "06".equals(cmd) && "61".equals(sr) -> "sendstart"
  "01".equals(sr) -> busy | "02".equals(sr) -> nochannel
  "07".equals(sr) -> kill | "09".equals(sr) -> cksum (BAD CHECKSUM)
  "70".equals(sr) -> getmessage | "71".equals(sr) -> putmessage
  "7e".equals(sr) -> msgtimeout
  "62".equals(sr) -> sendstop | "60".equals(sr) -> recstart
  "6f".equals(sr) -> recstop
  else -> FAIL
- IMPORTANT QUIRK: the module's immediate ACK to the 68 06 send-start
  frame is "68 06 00 01 87 F8 00 00 10" (byte[3]=0x01), so the stock app
  classifies it "busy" and retrySendATCmd() RESENDS the start frame up
  to MAX_RETRY times. The 68 06 02 61 "sendstart" notification only
  arrives ~0.5 s AFTER the KEY_DOWN ioctl -- i.e. the stock app's PTT
  keying is NOT gated on any serial reply; the notification is a
  consequence of keying, not a precondition. RumiTX therefore sends the
  frame and fires the ioctl immediately (no 2 s wait).
- retrySendATCmd(result, sr): on fail/busy/nochannel/kill/cksum with
  retry>0, resends the stored atCmd frame and decrements the counter
  (set to MAX_RETRY by sendATCommond); otherwise delivers
  DataInterface.sendATCmdResult(atCmd, result, sr) to the UI fragment.
- INBOUND SMS (68 11) PARSE (ReceiveDataPort.onReceive "11" branch,
  decoded 2026-10-11 run 9/16 -- no live sample yet, needs a 2nd DMR TX):
  len     = parseInt(hex.substring(12,16), 16)   // "00"+LEN field
  number  = parseInt(hex.substring(16,22), 16)   // BE int of payload[0:3]
  content = unicode2String(hex.substring(22, 22+(len-3)*2))
            // payload[3:len], NO trailer stripped
  The 3-byte header's internal layout (msgtype byte? pure sender ID?) is
  UNVERIFIED. unicode2String (StringUtils): for each 4-hex-char group,
  (char)parseInt(group,16). Ported to Dmr007Frame.unicodeToString() +
  parseSmsNotification() with self-tests (synthetic frame).
- 5-byte status frames observed live: "XX 00 FF A1 F1" (hex contains "00" =
  SUCCESS). Seen after APP_START ioctl and after a PTT down/up cycle. First
  byte varies (a1, 21) - likely a status/echo byte. NO reply seen within 3 s
  after 68 36, 68 06 start, or 68 06 stop frames.

68 07 SMS-SEND ACK QUIRK (decoded 2026-10-11 run 10/16 -- stock-app bug,
does NOT affect the module or RumiTX):

  ReceiveDataPort.atCmd.split(" ")[8] == "01" before it fires the "send"

STOCK RX PATH (SerialPortService$9 receive thread, DMR007 branch --
decoded 2026-10-11 run 10/16; RumiTX's 68..10 scanner is equivalent):
  Framing primitives in ATCommond:
  - checkHead(s) = s.startsWith("68")            (hex string, no spaces)
  - checkTail(s) = s.endsWith("10")
  - checkSerialDataLean(s): s = accumulated hex; if len<16 chars -> -1010;
    len = parseInt(hex[12:16],16) (bytes 6-7, the "00 LL" field); returns
    (18 + len*2) - s.length() = hex chars still needed for a full frame
    (0 = complete). The length lives at the same offset in every frame,
    including the 68 11 SMS notifications.
  - excisionExcessHead(s): hex->bytes, drop everything before the first
    0x68 byte, return the rest as hex. This is how the boot-indicator
    garbage ("44 c6 b5 b5 c0 31 3b 0d 0a", no 0x68) is discarded and the
    stream re-syncs ("serialData no HEAD" -> excise -> re-check).
  Reassembly: read chunk -> hex; if it starts with 68, compute lean and
  either dispatch the complete frame or accumulate and "goto read
  Remaining data" (100 ms sleeps between reads); complete frames go to
  the handler as Message(what=1, obj=hexString) -> ReceiveDataPort.
  NOTE: the stock loop has quirks (it dispatches via the handler in the
  "has HEAD" path and accumulates in another); the exact state machine
  was not fully traced, but the framing primitives above are exact and
  our scanner implements the same wire format.
