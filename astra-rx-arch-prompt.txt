RumiTX 2030 - DOOGEE S80 RX audio architecture question. We found the root cause, need your guidance on the cleanest fix.

WHAT WE PROVED TODAY (kernel logs + HAL disassembly)
- The stock Talkie app produces RX audio (static + voice) through the HIDL service vendor.hct.hardware.talkie@1.0-service.
- Kernel log during working stock RX shows this exact sequence:
    1. hct_eint_speaken_isr: enter  (GPIO interrupt fires)
    2. hct_wait_speak_en: enter     (HIDL service thread calls the ioctl)
    3. "before enable aw pa, sleep 100ms"  (driver powers the audio amplifier)
  The ioctl RETURNS. Audio flows.
- When our native daemon calls ioctl(/dev/hctintercom_node, 0x80046905, &int) directly, it blocks forever in hct_wait_speak_en. The interrupt never fires. We never did the GPIO setup.
- Before the working sequence, the HIDL service sets GPIO 58, 17, 18, 68 down (seen in dmesg from PID 7504 talkie@1.0-service).
- Disassembly of talkie.default.so speak_enable(): it just does ioctl(fd, 0x80046905, &stack_int), no magic. The fd comes from a global (opened in talkie_init). If ioctl fails it logs "Call cmd INTERCOM_SPEAK_ENABLE fail" and returns -1; on success it returns the int the kernel wrote back.
- Our current architecture: app -> TCP 127.0.0.1:45921 -> native daemon (started from adb shell) -> direct ioctl on /dev/hctintercom_node. TX works (KEY_DOWN 0x40046903). We never touch HIDL. We never touch GPIO.

THE CORE PROBLEM
The RX audio path requires a GPIO-triggered hardware interrupt BEFORE the SPEAK_ENABLE ioctl will return. The HIDL service owns that sequence. Our direct-ioctl bypass works for TX (which doesn't need the interrupt) but deadlocks on RX audio.

We cannot modify the kernel. Everything must work from userspace (adb shell daemon + Android app, no root at runtime on the app side; the daemon runs as shell).
