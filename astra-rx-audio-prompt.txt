RumiTX 2030 - DOOGEE S80 RX audio wall. Need your deepest Android kernel/driver knowledge. Copy-paste ready context below.

THE DEVICE
- DOOGEE S80 rugged phone, Android 8.1, MediaTek MT6763T (Helio P23).
- Built-in DMR/UHF talkie module (400-470 MHz). Two kernel interfaces:
  1. /dev/ttyMT1 - serial port to the DMR module. Speaks AT commands: AT+DMOSETGROUP= (channel program), AT+DMOSETVOLUME=, AT+DMOAUTOPOWCONTR=, AT+DMOMES=. init.talkie.rc sets ttyMT1 to 0666 on boot.
  2. /dev/hctintercom_node - world-writable char device. ioctl interface for PTT key down/up (vendor spelling is "ppt", not "ptt").
- Vendor HIDL service: vendor.hct.hardware.talkie@1.0::ITalkiePort/default. Methods: talkie_init, talkie_deinit, talkie_app_start, talkie_app_exit, talkie_ppt_down, talkie_ppt_up, talkie_speak_enable, talkie_speak_disable, talkie_update. Callback: reportResults.
- Exact ioctl table on /dev/hctintercom_node, recovered by disassembling /vendor/lib64/hw/talkie.default.so (64-bit):
    INTERCOM_APP_START      0x6901          (_IO('i',1))
    INTERCOM_APP_EXIT       0x6902          (_IO('i',2))
    INTERCOM_KEY_DOWN       0x40046903      (_IOW('i',3,int))  <- TX works through this
    INTERCOM_KEY_UP         0x40046904      (_IOW('i',4,int))
    INTERCOM_SPEAK_ENABLE   0x80046905      (_IOR('i',5,int))  <- BLOCKS FOREVER in kernel
    INTERCOM_SPEAK_DISABLE  0x6906          (_IO('i',6))
    INTERCOM_MODULE_UPDATE  0x6907          (_IO('i',7))
  NOTE the anomaly: SPEAK_ENABLE is the ONLY _IOR in the table - it reads an int FROM the driver. Every other call is _IO or _IOW. A "speaker enable" that reads back from the kernel smells like it waits on a driver-side event (RX audio frame? hardware ready signal?) that never arrives.
- Stock channel DB (com.android.talkie) has ONE frequency field plus separate txcxcss/rxcxcss columns. Frequency stored as MHz string with 4 decimals, e.g. "400.0420".

WHAT WORKS (SDR-verified, no root at runtime)
- Architecture: app -> TCP socket (127.0.0.1:45921) -> persistent helper daemon (must be started from adb shell with RUMITX_TCP=1, because Android 8+ silently blocks apps from exec'ing helper binaries) -> ioctl KEY_DOWN on /dev/hctintercom_node -> module transmits.
- Holding on-screen PTT produces a real 7dB RF burst at 446.5555 MHz on the SDR, timed with the button press. Physical side button (KEYCODE_F9) also transmits.
- Channel programming via AT+DMOSETGROUP works - the module tunes where we tell it.

WHAT IS BROKEN: RX AUDIO, completely
- Tuned to 460.075 MHz analog FM, squelch set to 0 (wide open monitor). Speaker output: ZERO. Not even static.
- The signal is definitely there - a separate professional radio on the same bench is receiving Beloit PD traffic on 460.075 right now.
- Suspected root cause: the HCT driver's speaker-enable ioctl BLOCKS FOREVER in the kernel. The hardware interrupt fires but the driver never wakes up. Calling that ioctl from our helper daemon freezes the daemon solid; one attempt froze the whole app (blank white screen, had to pull the call out).
- The stock Talkie app receives audio fine, so a working RX path EXISTS in this hardware. We just don't know which one it uses.

THE QUESTIONS

2. Why would the _IOR('i',5) speaker-enable ioctl block forever in-kernel with the IRQ firing? It is the only call in the table that reads FROM the driver, so it likely waits on a driver-side wait queue (RX audio frame ready? hardware ready signal?) that only wakes when some precondition is met. Candidates: INTERCOM_APP_START (0x6901) was never issued in our sequence; the DMR module must be put in RX/monitor state first via AT commands before the audio event can fire; or the stock app calls HIDL talkie_speak_enable which performs extra setup before the ioctl. Given the stock app works, which missing precondition is most likely, and is there a way to issue the ioctl non-blocking (O_NONBLOCK on the fd? or is the block inside the driver's unlocked_ioctl regardless)?
3. Is there a way to READ RX audio as PCM from the driver instead of relying on the speaker ioctl at all?
